FreeFinder restaurant gift codes

Scope: Starter Boost (1 day), Spotlight Boost (3 days) or City Push (8 days)
from activation, EUR 0, no payment and no
subscription. Individual codes are redeemable once, default to 30 days before
expiry and are bound to the supplied restaurant name. Redemption is available
in the native Business ads screens (requires the new app update) and on:
https://freefinder.at/business-promo.html

Shared evergreen code:
  npm run promos -- create --shared STARTERGRATIS --label "Native Starter Aktion"
  npm run promos -- create --shared SPOTLIGHTGRATIS --package spotlight --label "Native Spotlight Aktion"
  npm run promos -- create --shared CITYGRATIS --package city --label "Native City Aktion"
Create it only once. Re-creating an existing code is rejected and never resets
prior redemptions. One redemption per normalized restaurant name and full
address PER CODE, shared across iOS, Android and web. Each restaurant may use
each of these three codes once. Code does not expire; the ad lasts exactly
24, 72 or 192 hours according to the code's stored package. The shared code can be passed to selected restaurants;
it is not an authentication secret and can be forwarded by its recipients.
Without verified merchant accounts, self-declared identity cannot reliably
prevent deliberate impersonation, misspellings or changed addresses. The
server enforces atomic deduplication and rate limits, not proof of ownership.
Revoking a shared code stops new claims but preserves already-running ads.
Admin list includes the total redemption count, not restaurant contact data.

Create a code:
  npm run promos -- create --restaurant "Restaurantname" --label "Kontakt"
Add --package spotlight or --package city for the longer packages. The default
remains starter, including legacy stored records without packageId. --days
controls an individual CODE's validity, not the ad duration. Clients cannot
override duration, package or price. Native clients need the package-support
update to redeem 3/8-day codes; earlier Starter-only clients reject them.
The response contains a private code and ready-to-share redemption link. Keep
them out of Git, screenshots, public tickets and analytics. The full code is
returned once; the server only stores a hash and the final four characters.

List status / revoke an unused code:
  npm run promos -- list
  npm run promos -- revoke --id CODE_ID

Administration requires MERCHANT_PROMO_ADMIN_SECRET. The CLI also reads the
macOS Keychain entry service=freefinder-merchant-promo-admin, account=freefinder.
No credential belongs in the repository or frontend. Never reuse store keys.

Deployment:
  npm ci
  npm test
  npm run deploy
Keep existing Worker secrets and vars. MERCHANT_PROMOS is a SQLite Durable
Object, owning both redemption and campaign creation in one transaction.
Do not remove its binding, migration or class during future deployments.
Do not roll back to a pre-promo Worker blindly after this storage migration.

Campaigns are merged with the existing paid merchant feed. Native iOS and
Android already consume its schema. Paid purchase validation remains unchanged;
the regular deals.json, subscriptions and QR destination are not changed.
Expired gift ads leave this separate campaign feed after their selected duration;
this does not change automatic-removal policy for ordinary deals.

The website keeps the request ID in session storage to retry an interrupted
submission without creating a second ad or extending its lifetime. Reusing the
same request ID with changed data is rejected. Do not change the draft after

Referral source-receipt audit (disabled by default)

REFERRAL_RECONCILIATION_ENABLED=0 is separate from REFERRAL_MONTHS_ENABLED.
Both must be 1 before the existing ledger alarm performs source checks. Do not
activate either merely to test a deployment. Real Store permission/receipt tests,
legacy ownership migration, complete redemption and refund handling remain
release prerequisites. Deployment must preserve existing vars and secrets.

The audit rechecks only the friend's exact original qualifying trial receipt.
Each alarm scans at most 20 account records and reads at most two Store receipts;
unfinished scans continue after two minutes, completed cycles after 24 hours.
This is not an exact daily guarantee: Store failures, retries and queueing may
delay a cycle. A cursor and recoverable lease preserve progress. Account deletion,
newer proof reviews and concurrent preferences/redemption updates are retained.
The audit shares the existing alarm with rate cleanup and retains earlier alarms.
Changing a flag alone does not bootstrap an idle object: a verified account
request must first schedule its existing cleanup alarm. Confirm this deliberately
when enabling later; do not create a production referral or consume an offer.

Only private sourceReview/reconciliation metadata is added. Explicit source
revocation or uncertain/missing proof is flagged for manual review. Account
credit, redemption states and existing Store benefits are never automatically
deleted, undone or replayed. In particular, an already-applied inviter benefit
does NOT get reversed by this audit. Fresh redemption independently rechecks
source proof and holds uncertain/revoked sources without removing credit.
Historical missing evidence is not backfilled or guessed.

POST /api/referral-months/reconciliation-status with an empty JSON object and
x-freefinder-merchant-secret matching protected REFERRAL_ADMIN_SECRET returns
aggregate cycle counts and scheduling state only. It rejects regular account
authentication and has no public contact, receipt or account identifiers. No
admin secret is automatically provisioned. Keep it out of logs and shell history.
This status endpoint does not start a scan or financial operation. Individual
manual-review resolution and Store-side benefit reconciliation remain separate
work; do not treat an aggregate status as a completed referral lifecycle.
